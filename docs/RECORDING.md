# 목소리 준비 — 직접 녹음과 클론 병행

## 왜 병행인가
- **직접 녹음**: 화자의 존재가 필요한 곳. 숨·머뭇거림·웃음이 의미를 가지는 대목.
- **클론 TTS**: 정보 밀도가 높고 대본이 자주 바뀌는 곳. 문장만 고치면 다시 녹음할 필요가 없다.
- 두 소리가 "거의 같지만 미묘하게 다르면" 가장 어색하다. **같은 마이크·같은 방·같은 거리**로 참조를 뜨고, 최종 라우드니스를 같게 맞춘다(-16 LUFS, 40단계가 처리).

## 어디에 무엇을 쓰나 (기본값)
| 구간 | 목소리 | 이유 |
|---|---|---|
| 오프닝, 마무리·CTA | 직접 녹음 | 첫인상과 인사는 사람이어야 한다 |
| 판단·감정이 담긴 문장 | 직접 녹음 | 톤이 내용의 일부 |
| 절차·수치 설명, 인용문 낭독 | 클론 TTS | 반복·수정이 잦다 |
| 쇼츠 | 롱폼에서 쓴 음성 재사용 | 이음새 문제 없음 |

## 참조 음성 만들기 (클론용, 한 번만)
1. 조용한 시간, 창문 닫고, 마이크에서 25cm 안팎, 팝필터 사용.
2. **30~60초** 읽는다. 지문은 **실제 대본과 같은 문체**여야 그 문체로 말한다. 단정문·질문·숫자가 든 문장·마무리 인사를 골고루 섞으면 억양 폭이 넓어진다.
3. **무보정으로 저장**한다(노이즈 제거·EQ·컴프레서 전부 끄기). 클론은 처리된 소리까지 복제한다.
4. `voice.json`의 `ref_file` 이름으로 저장하고, 짧은 문장 두 개로 시험 생성해 확인한 뒤 전체에 적용한다.

## 녹음 품질 기준
| 항목 | 기준 |
|---|---|
| 신호대잡음비 | 30 dB 이상 |
| 무음 구간 RMS | -55 dB 이하 |
| 클리핑 | 0 샘플 |
| 길이 | 30~60초 |
| 받아쓰기 | 지문과 일치, 문장 누락 없음 |

측정:
```bash
ffmpeg -i 녹음.m4a -af ebur128=peak=true -f null -
ffmpeg -i 녹음.m4a -af "silencedetect=noise=-50dB:d=0.4" -f null -
```

**참조로 가공할 때는 두 가지만 맞춘다.** 음색을 건드리는 처리는 하지 않는다.
1. 60Hz 이하 럼블 제거 — 목소리 대역이 아니라 방·책상 진동이다.
2. 라우드니스를 **-18 LUFS**로 맞춘다 — 클론은 입력 레벨에 영향을 받는다.
```bash
ffmpeg -i 녹음.m4a -af "aformat=channel_layouts=mono,aresample=44100,highpass=f=60,loudnorm=I=-18:TP=-1.5:LRA=11" \
  -ar 44100 -ac 1 -b:a 192k channel_voice_ref.mp3
```

**채널·샘플레이트 변환은 `loudnorm` 앞에 둡니다.** 뒤에 두면 스테레오→모노 다운믹스가 채널당 0.7071 계수로 합쳐지는데, 좌우가 같은 신호(마이크 하나로 녹음하면 그렇습니다)면 √2 = **+3.01 dB** 가 리미터 **뒤에** 얹힙니다. TP=-1.5 로 지시해도 결과는 +1.5 가 됩니다. `loudnorm` 은 자기가 본 신호 기준으로 `output_tp: -1.50` 이라고 보고하므로 **로그만 봐서는 안 걸립니다.**

만든 뒤 검산합니다:
```bash
ffmpeg -i channel_voice_ref.mp3 -af ebur128=peak=true -f null - 2>&1 | grep -E " I:| Peak:" | tail -2
# I: -18 근처.
# TP 지시는 -1.5 지만 mp3 인코딩 오버슛으로 0.0~0.3 dB 올라올 수 있습니다(실측 -1.4 ~ -1.8).

# 판정은 이걸로 합니다 — 풀스케일 이상 샘플이 **0개**여야 합니다.
# ebur128 의 Peak 은 dBFS 로 반올림돼 찍혀서 -0.0 과 0.0 이 안 갈립니다.
ffmpeg -v error -i channel_voice_ref.mp3 -f f32le - | python3 -c \
  "import sys,numpy as np;x=np.frombuffer(sys.stdin.buffer.read(),'<f4');print('풀스케일 이상',int((abs(x)>=1).sum()),'개 / 최대',round(20*np.log10(abs(x).max()),2),'dBFS')"
```

**0개가 아니면 위 명령의 필터 순서가 틀린 것입니다** — 다운믹스가 리미터 뒤에 붙으면 `-1.5` 지시가 `+1.5` 로 나옵니다.
실측으로 순서가 틀렸을 때 199샘플, 고친 뒤 0샘플로 갈렸습니다. 잡아야 할 것이 판정선에서 1.2 dB 위라 오차로 놓칠 여지가 없습니다.
`-1.5 이하` 같은 선은 긋지 않습니다 — 정상이 떨어집니다(씬 원본은 -0.06 ~ -0.08 dBFS 로 나오고, 그걸 -16 LUFS 로 맞추는 것이 40단계 일입니다).

### 잴 때도 다운믹스하지 않습니다 — 같은 √2 가 측정 쪽에도 있습니다

위 함정은 **처리 순서**의 이야기인데, **재는 쪽에도 똑같이 있습니다.**

```
ffmpeg -nostdin -i <파일> -af ebur128=peak=true -f null -            ← 이렇게 잽니다
ffmpeg -nostdin -i <파일> -vn -ac 1 -af ebur128=peak=true -f null -  ← 피크가 3.01 dB 높게 나옵니다
```

`-ac 1` 이 채널당 0.7071 로 합치므로 dual-mono 파일이면 **√2 = +3.01 dB** 가 붙습니다.
E01 인트로 세 클립이 전부 dual-mono 라 셋 다 **정확히 3.0 dB** 갈렸습니다(-4.6 대 -1.6 등).

**`I`(라우드니스)는 두 방법이 같습니다.** EBU R128 이 스테레오를 두 채널 합으로 재고 √2 다운믹스가
그 합을 보존해서입니다. **`I` 가 같다고 피크도 같을 거라 넘겨짚으면 여기서 걸립니다.**

**클리핑 판정은 파일 그대로, `|x| >= 1.0` 샘플 수로** 봅니다(`common.py` 의 `clipped()`).

### 채널 수가 바뀌면 3.01 dB 이 움직입니다 — 세 자리가 같은 √2 입니다

> **채널 수가 바뀌면 3.01 dB 이 움직인다. 줄이면 피크가 오르고, 늘리면 라우드니스가 오른다.**
> **두 수를 비교하기 전에 채널 수가 같은지 본다.**

| 언제 | 무엇이 3.01 움직이나 | 증상 |
|---|---|---|
| 처리에서 다운믹스가 리미터 **뒤** | 피크 | `TP=-1.5` 지시가 `+1.5` 로 나온다 |
| **잴 때** 다운믹스(`-ac 1`) | 피크 | -4.6 이 -1.6 으로 보인다 |
| 모노를 **스테레오에 얹을 때** | 라우드니스 | -16 이 -13 으로 잡힌다 |

**앞의 둘은 「내가 다운믹스해서」이고 셋째는 「누가 스테레오로 복제해서」입니다.**
방향이 반대라 더 안 이어집니다 — 앞은 채널을 줄이는 것이고 뒤는 늘리는 것입니다.

**뒤 문장이 E01 에서 실제로 필요했던 것입니다.** 내레이션(모노 `-16`)과 인트로 클립(스테레오 `-18`)을
빼서 「2 LU 차이」로 정했는데, 스테레오 마스터에서 내레이션만 `+3.01` 로 잡혀 **실제 의도는 5 LU** 였습니다
(마스터 실측 3.9 LU). **두 수가 다 맞고 이름도 다 맞는데, 둘을 빼면 안 되는 수였습니다.**

**값이 있는 곳**: `common.py` 의 `NAR_LUFS` · `40_nar_finalize.py` 의 필터 순서.
그 둘은 값과 「어느 기준인지」까지만 두고 **이유는 여기로 옵니다**(음악 감독).

### 길이는 무엇을 재는지 밝힙니다

한 파일에 값이 셋이고 서로 다릅니다.

```
컨테이너      ffprobe -show_entries format=duration        가장 긴 스트림 기준
스트림        ffprobe -select_streams a:0 stream=duration  그 트랙만
디코드 샘플    디코드한 샘플 수 / 샘플레이트                 aac 프라이밍 때문에 또 다릅니다
```

E01 `intro_orig` 이 **컨테이너 9.242 · 영상 9.209 · 소리 9.192** 입니다. 요구값과 맞는지 볼 때
어느 것을 보느냐로 결론이 갈립니다 — **오디오 스트림이 9.191995 로 요구 9.192 와 같고**,
컨테이너가 0.05초 긴 것은 영상 트랙의 GOP 경계입니다.

## 참조 길이 — 실측
같은 녹음에서 전체(약 50초)와 앞부분 발췌(약 20초)를 참조로 각각 생성해 두 지문으로 비교한 결과, 전체 쪽이 매번 근소하게 나았다.

| 참조 | 음색 유사도 | 음높이 차이 |
|---|---|---|
| 전체 50초 | 0.9955 / 0.9916 | -7Hz / -3Hz |
| 발췌 20초 | 0.9936 / 0.9896 | -10Hz / -6Hz |
| (참고) 다른 화자 | 0.890 | +60Hz |

두 지점만 비교한 것이라 "길수록 좋다"고 단정할 수는 없다. 발췌본은 전체의 부분집합이라 길이 때문인지 억양 다양성 때문인지도 갈리지 않는다. 실무 결론은 **전체 녹음을 쓰는 쪽이 안전하다**.

## 직접 녹음해서 공정에 넣기
1. 씬 단위로 하나씩 녹음한다. 파일명은 씬 id 그대로: `<EP>/audio/nar_raw/s00.wav`
   - wav 권장(44.1kHz 이상, 모노). mp3·m4a도 받는다.
   - **씬 하나를 한 테이크로.** 틀리면 그 씬만 다시 간다. 이어붙이지 않는다.
   - 앞뒤로 1초쯤 여백을 둔다. 40단계가 잘라낸다.
2. TTS 씬과 녹음 씬을 섞어도 된다. `20_tts_generate.py --ids`로 TTS 씬만 생성하고 나머지는 녹음 파일을 같은 폴더에 둔다.
3. 이후는 동일하다. `30_nar_check.py` → `40_nar_finalize.py`. 검사는 녹음본에도 그대로 쓴다.

## 검증
```bash
python3 pipeline/voice_similarity.py <참조> <생성물...>
```
같은 화자면 음색 유사도 0.99 이상·음높이 차이 10Hz 이내, 다른 화자면 0.89 수준·60Hz 차이로 갈린다(실측).

## 주의
- 녹음 환경이 바뀌면(방·마이크·거리) 참조도 다시 떠야 이음새가 안 생긴다.
- 컨디션이 다른 날 녹음한 씬은 같은 편 안에서 튄다. 한 편은 되도록 하루에.
- 참조를 바꾸면 그 이후 편의 목소리가 전부 바뀐다. 바꾼 날짜를 기록해 둘 것.
