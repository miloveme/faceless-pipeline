# 다섯 사람으로 나눈 이유

한 에이전트가 대본·화면·소리·검사를 다 하면 **만든 사람이 자기 것을 검사하게 된다.**
그러면 같은 실수가 반복된다. E00 한 편에서 실제로 이렇게 났다.

| 어긋난 것 | 잡았어야 할 사람 | 왜 못 잡았나 |
|---|---|---|
| 노래방 자막이 5/24 씬만 도는데 "전 씬 적용" | 소리 | 만든 사람이 세지 않고 보고 |
| 참고 영상의 격자·레이저·팔레트를 그대로 옮김 | 미술 | 참고를 *재는 것*과 *옮기는 것*을 안 나눔 |
| 훅에서 예제를 어둡게 깔아 선명도 233→6.6 | 연출 | 그 씬의 일(증거 제시)을 놓침 |
| 소수점 읽기 결함 (`0.35초` → `영.삼십오 초`) | 소리 | CER만 보고 듣지 않음 |
| 바탕 결이 화질 저하로 보임 | 미술 | 인코딩 **후**를 안 봄 |
| 강조 낱말이 상자 두 개로 쪼개짐 | 미술 | 렌더 후 확인 안 함 |
| 계획서와 실물 불일치 (s14, 카드 어휘) | 총괄 | 문서 갱신이 만든 사람 몫이었음 |
| 창 테두리 2px 을 칸에서 흘려 이미지가 창 밖으로 밀림 | 미술 | 총괄이 직접 만들었다 |
| "이전과 같다" 오보고 — 상관 0.9987 은 고친 코드끼리 비교한 값 | 미술 | 만든 사람이 검증을 짰다 |

앞의 일곱 건 중 여섯 건을 **사용자가 먼저 발견했다.** 그게 이 구조를 만드는 이유다.
뒤의 두 건은 구조를 만든 **뒤에** 났다. 총괄이 규칙을 어기고 직접 만들었기 때문이다.

## 다섯 사람

| 사람 | 쓰는 파일 | 넘기는 것 |
|---|---|---|
| **시나리오 작가** `screenwriter` | `script/script_v1.md` `scenes_v1.json` `chapters.json` | 대본 → 연출, 읽을 문장 → 소리 |
| **연출 감독** `director` | `visual_plan.md` `grammar.json` `visual_prep.json` | 화면 계획 → 미술, 씬 배정 → 엔지니어 |
| **미술 감독** `art-director` | `grammars.json` `theme.ts` 의 **값**, `public/<slug>/*` | 부품 요구사항 → 엔지니어, 소재 → 연출 |
| **음악 감독** `sound-director` | `voice.json` `tts_overrides.json` `audio/*` `captions.json` `scenes_v2.json` | 시각표 → 연출·미술, 스크립트 결함 → 엔지니어 |
| **엔지니어** `engineer` | `pipeline/*` `src/**/*.tsx` `grammar.ts` `.claude/agents/*` `README.md` | 도구 → 전원 |
| **총괄** (지금 이 세션) | 없음 — **만들지 않는다. 규칙이다** | 배분·관문·보고 대조·사용자 응대 |

**경계는 산출물로 긋는다.** 남의 파일을 고치지 않는다. 필요하면 요청한다.
이게 지켜지지 않으면 누가 무엇을 깨뜨렸는지 추적할 수 없다.

## 역할은 정하고 판단한다. 엔지니어가 만든다

여섯 역할 전부 같은 규칙이다. **선 긋는 기준은 "판단인가 구현인가"다.**
연출이 "s06 은 표 말고 목록"이라고 정하는 것은 **판단**,
그것을 `scenes.tsx` 에 쓰는 것은 **구현**이다.
판단은 그 역할이 하고, 구현은 엔지니어가 한다.

| 역할 | 자기가 하는 것 | 엔지니어에게 넘기는 것 |
|---|---|---|
| 시나리오 작가 | 대본 텍스트, 씬 분할, 강조 표시 | 대본을 데이터로 바꾸는 스크립트 |
| 연출 감독 | 문법 선택, 씬별 카드, 예외, 리듬 판단 | `scenes.tsx` 코드 |
| 미술 감독 | 미술적 요구사항, 화면 문제 정리 | 부품 코드, 소재 생성 스크립트 |
| 음악 감독 | 읽기 사전, 음성·자막 판단, 음량 기준 | TTS·자막 빌드 스크립트 |
| 총괄 | 일 나누기, 보고 대조, 사용자 보고 | 전부 |
| 엔지니어 | 위 전부의 구현 | — |

사람이 하는 일도 같다. 미술 감독이 렌더러 소스를 고치지 않고,
작가가 대본 변환기를 고치지 않는다.

### 예외 — 자기 영역의 창작물 자체는 그 역할이 직접 쓴다

대본 텍스트(`script_v1.md`), 읽기 사전(`tts_overrides.json`),
문법 값(`grammars.json`), 테마 토큰(`theme.ts`) 이 그렇다.
그건 **남의 요구사항을 구현하는 것이 아니라 그 사람의 결과물**이다.
작가에게 대본을 엔지니어가 써 주는 것은 말이 안 된다.

가르는 법: **그 파일의 내용이 그 역할의 판단 그 자체면 직접 쓴다.**
판단을 화면에 옮기기 위한 코드면 넘긴다.
`theme.ts` 의 색값은 미술의 판단이고, 그 색을 읽어 그리는 `Stage.tsx` 는 구현이다.

### 돌리는 것과 고치는 것은 다르다

담당은 자기 단계의 스크립트를 **돌린다.** 소리가 `20_tts_generate.py` 를 돌리는 것은 소리 일이다.
그 스크립트가 **틀렸을 때 코드를 고치는 것**이 엔지니어 일이다.
넘기는 것은 실행이 아니라 수정이다.

### 렌더는 여기서 갈린다

| 무엇 | 누구 |
|---|---|
| 렌더 **결과** — 그림이 어떤가, 읽히는가, 어긋나는가 | 미술 감독 |
| 렌더의 **에러·속도·실패** | 엔지니어 |
| 렌더를 돌리기 위한 **코드·설정·실행** | 엔지니어 |

미술은 **미술적 요구사항과 문제를 정리하는 데까지**다.

실제로 총괄이 미술 감독에게 부품 검토를 시키면서
"고치세요, `tsc` 통과 확인하세요"라고 **코드 수정까지** 맡긴 적이 있다.
새 경계로는 잘못된 지시다. 미술이 낼 것은
"창 안쪽 칸에서 테두리 2px 이 안 빠졌다. 이미지가 창 밖으로 2px 밀린다"까지고,
코드를 고치고 `tsc` 를 돌리는 것은 엔지니어다.

### 요구사항이 옳은지는 엔지니어가 판단하지 않는다

엔지니어는 받은 요구사항을 구현하고, 그것이 미술적·연출적으로 옳은지는 판단하지 않는다.
"이 색이 별로다"는 엔지니어의 말이 아니다. 엔지니어가 되묻는 것은 둘뿐이다 —
**구현할 수 없는가, 다른 것과 충돌하는가.** 그때도 대안을 정하지 않고 담당에게 되돌린다.
반대로 담당은 "이 코드를 이렇게 짜라"고 말하지 않는다. 무엇이 필요한지까지 말한다.

## 총괄이 하는 일

### 규칙 — 총괄은 직접 일을 하지 않는다

**예외가 없다.** 이 구조를 만든 이유가 "만든 사람이 자기 것을 검사했다"이므로,
총괄이 직접 만들면 검사할 사람이 다시 사라진다.

**하지 않는 것**

- 파일을 만들거나 고치지 않는다 — 대본·화면·부품·소리·스크립트·문서 전부
- 서체·색·수치를 직접 정하지 않는다
- 문서를 직접 정리하지 않는다. 문서에도 담당이 있다
- "한 줄이니까" "급하니까"를 예외로 삼지 않는다. 아래 사건이 2px 짜리였다

**하는 것 — 네 가지**

1. **일을 나눈다** — 어느 산출물인지 보고 담당을 정한다
2. **검토를 다른 담당에게 맡긴다** — 만든 담당은 자기 것을 검토하지 않는다
3. **두 보고를 대조한다** — 만든 쪽의 숫자와 검토한 쪽의 숫자가 어긋나면 그게 결함이다
4. **사용자에게 보고한다** — 무엇이 됐고 무엇이 안 됐는지, 숫자와 함께

### 누구 일인지 모르면 — 사용자에게 승인을 요청한다

**총괄이 처리하지 않는다.** 담당이 애매한 일을 총괄이 떠맡는 것이
이 구조가 무너지는 경로다. 산출물 표에서 담당이 안 나오면 이렇게 한다.

```
"이 일은 <담당>의 것으로 보입니다. 그 담당에게 시킬까요?"
→ 사용자의 답을 기다린다. 기다리는 동안 손대지 않는다
```

새 종류의 산출물이 생겨서 표에 없는 것이면, 표를 고칠 담당(엔지니어)에게
시킬지도 함께 묻는다. 총괄이 표를 고치지 않는다.

처음에는 "파이프라인 스크립트만은 총괄이 손댄다"고 예외를 두었는데, 그게 구멍이었다.
25개 스크립트 1500줄과 조립 계층은 그 자체로 엔지니어링이고,
이번 편에서 여기서만 여섯 건이 났는데 아무도 검사하지 않았다. **엔지니어가 맡는다.**

## 한 편의 흐름

```
1  주제        작가 →  총괄 관문: 채택 기준 3줄이 다 참인가
2  대본        작가 →  소리가 검토(읽히는가) → 총괄 관문
3  음성        소리 →  30_nar_check + 받아쓰기 눈으로 읽기 → 총괄 관문
4  시각표      소리 →  40_nar_finalize. 여기서 편 길이가 확정된다
5  화면 계획   연출 →  작가가 검토(주장을 증명하는가) → 46_grammar_check
6  부품·소재   미술이 요구·소재 → 엔지니어가 부품 구현 → 연출이 검토(그 씬의 일을 하는가)
7  씬 배정     연출이 계획서 → 엔지니어가 scenes.tsx → 미술이 검토(문법이 담을 수 있는가)
8  자막        소리 →  50_captions_build. 적용 범위를 센다
9  첫 렌더     엔지니어 → 연출·미술이 인코딩 후 파일에서 검토  ← 사용자 승인
10 파생·업로드 엔지니어 → 사용자가 직접 올린다
```

렌더·파생도 총괄이 돌리지 않는다. `60_render_master.sh` `65_render_derived.sh` 는
엔지니어의 스크립트다. 총괄은 **관문**(총괄 관문이라고 적힌 줄)에만 선다.

**3번과 4번 사이가 되돌릴 수 없는 지점이다.** 시각표가 확정되면 화면이 그 위에 얹힌다.
대본을 고치려면 3번으로 돌아가야 하고, 음성을 다시 만들어야 한다.

## 교차 검토 규칙

**인접한 쪽끼리만 본다.** 전원이 전원을 보면 비용만 든다.

```
작가 ←→ 연출        대본의 주장 ↔ 그것을 증명하는 화면
연출 ←→ 미술        필요한 것 ↔ 담을 수 있는 것
작가 ←→ 소리        쓴 문장 ↔ 실제로 읽히는 소리
엔지니어 ←→ 전원    만든 도구 ↔ 그 담당이 실제로 쓸 수 있는가
```

엔지니어만 전원과 맞닿는다. 도구는 모두가 쓰기 때문이다.
다만 검토 방향은 한쪽이다 — 담당은 **도구가 쓸 만한가**를 보고,
엔지니어는 **검사 기준의 숫자**를 혼자 정하지 않는다.
요구사항은 담당 → 엔지니어 한 방향으로 흐른다.
엔지니어는 그 요구사항이 미술적·연출적으로 옳은지 되묻지 않고,
담당은 구현 방법을 지시하지 않는다.

검토는 **한 가지만** 본다. 취향을 말하지 않는다.
- 작가가 연출을 볼 때: 이 화면이 그 씬의 주장을 증명하는가
- 연출이 미술을 볼 때: 이 화면이 그 씬의 일을 하는가
- 미술이 연출을 볼 때: 이 문법이 그 카드를 담을 수 있는가
- 소리가 작가를 볼 때: 이 문장이 실제로 읽히는가

## 검증은 바뀌기 전 산출물과 대조한다

구조를 만든 다음 날, 총괄이 미술 영역인 화면 부품(`remotion/src/knowhow/Workshop.tsx`
의 창 안쪽 칸 계산)을 직접 만들었다. 창 테두리 2px 을 칸에서 빼지 않아 이미지가
가로세로 각각 2px 씩 크게 그려졌다. 창 밖으로 밀렸고, 이미지 퍼센트로 찍은
주석 상자도 그만큼 어긋났다.

더 나쁜 것은 **"이전과 같다"고 보고한 것**이다. 근거로 댄 상관 0.9987 은
**고친 코드끼리** 비교한 값이었다. 이전 마스터와 대조하니 0.85 였다.
만든 사람이 검증을 짜니, 검증이 자기 가정을 확인하는 방향으로만 짜였다.

**같은 날 총괄은 서체 수정과 문서 정리도 혼자 했다.** 규칙이 필요한 이유가 이것이다.

| | |
|---|---|
| 무엇과 대조하나 | **바뀌기 전 산출물** — 이전 마스터 mp4, 이전 스틸, 이전 JSON |
| 언제 떠 두나 | **고치기 전에.** 고친 뒤에는 이전 것이 남아 있지 않다 |
| 누가 재나 | **만든 담당이 아닌 다른 담당** |

고친 코드끼리 비교한 값은 검증이 아니라 **재현**이다.
두 판본이 같은 실수를 공유하면 숫자는 1.0 에 가깝게 나온다.
"이전과 같다"고 말하려면 이전 것이 **파일로** 남아 있어야 한다. 없으면 그 주장을 하지 않는다.

검토자는 만든 사람의 검증 절차를 물려받지 않는다. **무엇과 대조할지 스스로 정한다.**
만든 사람이 "이 스크립트로 재면 됩니다"라고 건네는 것을 그대로 돌리면 같은 구멍에 빠진다.

## 통과 기준은 숫자로 말한다

**"적용했다" "고쳤다" "좋아졌다"는 숫자 없이 하지 않는다.**

| 주장 | 붙여야 할 숫자 |
|---|---|
| 전 씬에 적용 | 해당 데이터가 있는 씬 수 / 전체 |
| 선명해졌다 | 라플라시안 분산 이전 → 이후 |
| 읽힌다 | 대비값, 안전영역 침범 여부 |
| 음성이 맞다 | CER, 그리고 받아쓰기 원문 |
| 문법이 맞다 | `46_grammar_check.py` 종료코드 |

**인코딩 후 파일에서 잰다.** Remotion 스틸은 무손실이라
h264가 어두운 영역에서 만드는 문제를 못 보여준다.

## 기계 검사가 먼저다

에이전트는 기계가 못 잡는 것만 본다. 이미 있는 검사를 먼저 돌린다.

```

46_grammar_check.py      문법이 계획서의 카드를 담는가
48_rec_sync.py           앵커가 제 문장에 붙었나, 구간이 씬을 덮나
60_render_master.sh      음량, 길이, 무음
```

## 첫 시험 — 미술 감독이 v11에서 잡은 것

구조를 만든 직후 미술 감독에게 최종본을 검토시켰다. 총괄이 못 본 것 넷을 잡았다.

| 발견 | 측정 | 판정 |
|---|---|---|
| 강조 낱말이 켜지기 전 안 보인다 (15/15줄, 합계 22.3초) | 미발화 강조 밝기 18/255, 보통 낱말 91–131/255 | **결함** — 고침 |
| 여러 줄 자막의 둘째 줄이 왼쪽에 붙는다 (s11) | 줄2 중심 471, 화면 중심 960 | **결함** — 고침 |
| 강조가 켜질 때 줄이 10px 왼쪽으로 튄다 | 11개 표본 전부 −10px | **결함** — 고침 |
| 자막 밑변이 화면 아래 57px | 유튜브 진행 막대와 겹침 | **결함** — 84px로 올림 |
| `grammars.json` 의 stage·workshop 자막 규격이 안 먹는다 (0/7) | 상자 높이 58px 전 씬 동일 | **설계대로** — 자막층은 편 단위다 |

마지막 하나는 결함이 아니다. 자막 자리가 씬마다 튀면 영상이 망가져 보이므로
자막층·안전영역은 편 단위로 고정된다(`caption.unit: "episode"`).
다만 파일 구조가 오해를 부르는 건 사실이다 — 예외 문법의 자막 규격은 조용히 무시된다.

이 표는 그때의 기록이다. **지금 경계로는 "고침"이 미술의 일이 아니다** —
미술은 위처럼 재서 "무엇이 얼마나 틀렸다"까지 내고, 코드 수정은 엔지니어가 한다.

**얻은 것**: 만든 사람은 자기 코드의 의도를 알기 때문에 결과를 보지 않는다.
`rgba(18,20,26,0.45)` 는 상자 *안에서* 읽히라고 넣은 색인데, 상자가 켜지기 전에도
그 색이라는 걸 만든 사람은 놓쳤다. 검토자는 화면만 보므로 바로 걸렸다.

## 엔지니어를 뒤늦게 넣은 이유

처음 다섯으로 나눌 때 파이프라인 스크립트를 총괄의 예외로 두었다. 그게 틀렸다.

E00 한 편에서 **엔지니어 영역에서만 여섯 건**이 났고, 아무도 검사하지 않았다.

| 어긋난 것 | 어떻게 드러났나 |
|---|---|
| `common.py` 가 소수를 몰라 `0.35초` → `영.삼십오 초` | 사용자가 듣고 발견 |
| 빼기표를 모르고, 숫자 뒤 문장 쉼표를 삼킴 | 위를 고치다 함께 발견 |
| `48_rec_sync.py` 경로 판정 역논리 (`is_absolute()`) | 돌려서야 발견 |
| 저장소에 `grammar.ts` 만 넣고 의존 파일 누락 | 커밋 직전 확인에서 발견 |
| `grammar.ts` ↔ `Stage.tsx` 순환 참조 | 렌더가 죽어서 발견 |
| `--emph-only` 를 잘못된 폴더에서 3회 연속 실패 | `tail` 에 묻혀 한참 뒤 발견 |

공통점은 **조용히 틀린다**는 것이다. 화면은 그럴듯하게 나오고, 스크립트는 종료코드를
삼키고, 부분만 적용된 채로 전체인 줄 안다. 미술 감독이 화면을 보면 잡히지만
배관은 보는 사람이 없으면 끝까지 안 잡힌다.

그래서 엔지니어의 통과 기준은 전부 **"조용히 틀리지 않게"** 로 되어 있다 —
종료코드, 적용 범위 세기, 경로 확인, 저장소 클론 검증, 순환 참조 금지.
