# 여섯으로 나눴다가 둘로 돌아온 이유

한 에이전트가 대본·화면·소리·검사를 다 하면 **만든 사람이 자기 것을 검사하게 된다.**
그러면 같은 실수가 반복된다. E00 한 편에서 실제로 이렇게 났다.

| 어긋난 것 | 잡았어야 할 사람 | 왜 못 잡았나 |
|---|---|---|
| 노래방 자막이 5/24 씬만 도는데 "전 씬 적용" | 소리 | 만든 사람이 세지 않고 보고 |
| 참고 영상의 격자·레이저·팔레트를 그대로 옮김 | 미술 | 참고를 *재는 것*과 *옮기는 것*을 안 나눔 |
| 훅에서 예제를 어둡게 깔아 선명도 233→6.6 | 연출 | 그 씬의 일(증거 제시)을 놓침 |
| 소수점 읽기 결함 (`0.35초` → `영.삼십오 초`) | 소리 | CER만 보고 듣지 않음 |
| 바탕 결이 화질 저하로 보임 | 미술 | 인코딩 **후**를 안 봄 |
| 강조 낱말이 상자 두 개로 쪼개짐 | 미술 | 렌더 후 확인 안 함 |
| 계획서와 실물 불일치 (s14, 카드 어휘) | 총괄 | 문서 갱신이 만든 사람 몫이었음 |
| 창 테두리 2px 을 칸에서 흘려 이미지가 창 밖으로 밀림 | 미술 | 총괄이 직접 만들었다 |
| "이전과 같다" 오보고 — 상관 0.9987 은 고친 코드끼리 비교한 값 | 미술 | 만든 사람이 검증을 짰다 |

앞의 일곱 건 중 여섯 건을 **사용자가 먼저 발견했다.** 그래서 여섯으로 나눴다.
뒤의 두 건은 나눈 **뒤에** 났다. 총괄이 규칙을 어기고 직접 만들었기 때문이다.

## 둘로 돌아왔다 — 2026-09-13

여섯(작가·연출·미술·소리·엔지니어·검수자)에 총괄까지 일곱이었다. 사용자가 「토큰은 많이 드는데
그만큼 좋아지지 않는다」고 했고, 재 보니 맞았다.

**비용.** 담당을 띄울 때마다 `CLAUDE.md` 12.8KB + 정의 5~9KB 가 다시 깔린다. 컨텍스트가 안 이어져
같은 대본·`scenes.tsx` 를 담당마다 다시 읽는다. 값 하나 바꾸는 데 연출 판단 → 총괄 → 엔지니어 구현
→ 총괄 → 검증 다섯 홉. 담당 여섯이면 열다섯 쌍이고 메시지가 엇갈려 같은 보고가 두 번 오갔다.

**값.** 하루에 결함 다섯이 잡혔는데 무엇이 잡았는지 가르면 —

| 잡힌 것 | 무엇이 잡았나 |
|---|---|
| 문서가 가리키던 `attempt` 옵션이 코드에 없음 | 다른 역할이 코드를 열어 봄 |
| `voice.json` 미분류 키 7개 | 다른 역할이 파일을 셈 |
| `Root.tsx` 가 클론을 깸 | **새 클론에서 `tsc`** 를 돌림 |
| `check_private.py` 관문 구멍 | **빈 저장소로 전후 측정** |
| `AGENTS.md` 에 검수자 누락 | 파일을 읽음 |

**다섯 중 둘만 역할 분리에서 나왔고, 나머지 셋을 잡은 것은 절차였다** — 사람이 아니라 검사.
그리고 그 둘도 「음악 감독」이라는 상시 자리가 아니라 **"이 문장이 코드와 맞는지 재라"는 한 가지
질문**이 잡은 것이다. 그런 질문은 이제 `check_docs_cli.py` 가 매 커밋마다 한다.

6,600줄짜리 「영상 만드는 법」이 있고 만들어진 영상은 한 편, 그것도 아직 못 올린 상태였다.
최근 20커밋이 영상 내용물을 건드린 것이 0건이었다.

**그래서 역할은 줄이고 검사를 늘렸다.** 하루에 검사 8개를 만들어 관문에 걸었고(`60` 2개→8개,
`85` 셋→넷, 훅 6개), 그 다음 날 역할을 둘로 줄였다. 사람을 빼는 자리에 스크립트가 먼저 서 있어야
E01 때 못 잡던 것을 다시 못 잡는 일이 없다.

## 둘

| 사람 | 하는 것 | 안 하는 것 |
|---|---|---|
| **제작** (지금 이 세션) | 대본 → 화면 → 소리 → 렌더 → 커밋 → push. 한 편 끝까지 | 서버가 안 붙을 때 파고들기 · 검사 기준을 자기 결과에 맞추기 · 검수자 미루기 |
| **검수자** `final-editor` | 완성본을 처음부터 끝까지, 보는 사람의 눈으로 | 아무것도 만들지 않는다. 고치는 법을 쓰지 않는다. 제작의 목록을 먼저 받지 않는다 |

**만든 사람이 자기 것을 검사하는 문제**는 그대로 있다. 셋이 나눠 막는다 —
잴 수 있는 것은 **관문**, 잴 수 없는 것은 **검수자**, 「고쳤다」는 말은 **바뀌기 전 산출물과 대조한 숫자**.

작가·연출·미술·소리가 각자 갖고 있던 통과 기준과 실측 규칙은 `skills/knowhow-episode/SKILL.md` 의
1·2·3단계로 옮겼고, 엔지니어의 코드 규칙은 `pipeline/README.md` 「스크립트를 쓸 때」로 옮겼다.
파일이 사라져도 규칙은 남는다.

## 한 편의 흐름

```
1  대본        제작 → 05·10 검사                                    ← 사용자 승인
2  음성        제작 → 20·30·40. check_readings 가 10 앞에서, _coverage 가 50·55 끝에서
3  시각표      40_nar_finalize. 여기서 편 길이가 확정된다 — 되돌릴 수 없는 지점
4  화면 계획   제작 → 45 → 46 (담기·연속·이유·어휘)
5  렌더        제작 → 60 → 검사 8개 (음량·무음·문법·찌그러짐·가리킨 칸·정지·선명도·낡은 원본)
                                                                    ← 사용자 승인 (첫 렌더)
6  검수        검수자가 마스터를 본다. 목록 없이. 시각과 함께 낸다
7  고침        제작 → 다시 60. 검수자에게는 「고친 데가 나아졌나」만
8  관문        85 — 대장 · 판본 · 검수자 판정 · 끝맺음
9  push        pre-push — 개인 자산 · import · 새 클론 빌드
                                                                    ← 사용자가 올린다
```

**3번이 되돌릴 수 없는 지점이다.** 시각표가 확정되면 화면이 그 위에 얹힌다.
대본을 고치려면 2번으로 돌아가 음성을 다시 만들어야 한다.

## 검증은 바뀌기 전 산출물과 대조한다

구조를 만든 다음 날, 총괄이 미술 영역인 화면 부품(`remotion/src/knowhow/Workshop.tsx`
의 창 안쪽 칸 계산)을 직접 만들었다. 창 테두리 2px 을 칸에서 빼지 않아 이미지가
가로세로 각각 2px 씩 크게 그려졌다. 창 밖으로 밀렸고, 이미지 퍼센트로 찍은
주석 상자도 그만큼 어긋났다.

더 나쁜 것은 **"이전과 같다"고 보고한 것**이다. 근거로 댄 상관 0.9987 은
**고친 코드끼리** 비교한 값이었다. 이전 마스터와 대조하니 0.85 였다.
만든 사람이 검증을 짜니, 검증이 자기 가정을 확인하는 방향으로만 짜였다.

**같은 날 총괄은 서체 수정과 문서 정리도 혼자 했다.** 규칙이 필요한 이유가 이것이다.

| | |
|---|---|
| 무엇과 대조하나 | **바뀌기 전 산출물** — 이전 마스터 mp4, 이전 스틸, 이전 JSON |
| 언제 떠 두나 | **고치기 전에.** 고친 뒤에는 이전 것이 남아 있지 않다 |
| 누가 재나 | **관문 스크립트, 또는 검수자.** 만든 사람이 검증 절차를 짜지 않는다 — 대조 대상은 파일로 남은 이전 판본이다 |

고친 코드끼리 비교한 값은 검증이 아니라 **재현**이다.
두 판본이 같은 실수를 공유하면 숫자는 1.0 에 가깝게 나온다.
"이전과 같다"고 말하려면 이전 것이 **파일로** 남아 있어야 한다. 없으면 그 주장을 하지 않는다.

검토자는 만든 사람의 검증 절차를 물려받지 않는다. **무엇과 대조할지 스스로 정한다.**
만든 사람이 "이 스크립트로 재면 됩니다"라고 건네는 것을 그대로 돌리면 같은 구멍에 빠진다.

## 크기는 중립, 판정은 색 — 그리고 차이는 그대로 둔다

연출과 음악 감독이 각자 실측으로 같은 자리에 닿았다. 화면과 소리를 넘나드는 규칙이라 여기 둔다.

```
화면    크기는 중립, 판정은 색
소리    음량은 중립, 차이는 그대로
```

**둘을 나란히 놓고 보이는 편에서는 크기·음량이 판정으로 읽힌다.** 큰 쪽이 옳은 쪽이고,
큰 소리가 진짜다. 그래서 **비교의 축이 아닌 것은 맞춰 놓고, 판정은 색이나 라벨처럼
읽는 사람이 판정으로 알아보는 장치로만 한다.**

| 누가 | 무엇을 했나 | 왜 |
|---|---|---|
| 연출 | s05 의 두 조건 칸을 **238 대 237** 로 맞췄다 | 큰 쪽이 옳은 쪽으로 읽히고 있었다 |
| 음악 | 인트로 원본·클론의 **4.6 LU 차이를 없앴다** | 큰 쪽이 「더 진짜」로 읽힌다 |
| 음악 | s18 꼬리를 **통짜와 같은 게인**으로 뒀다 | 2.3 dB 크면 「상기」가 「강조」가 된다 |
| 엔지니어 | 썸네일 두 칸의 **얼굴 크기**를 502 대 500 으로 맞췄다 | 배율을 묶었더니 얼굴이 1.6배 차이로 남았다 |
| 연출·미술 | 인트로에서 원본·클론의 **화면비 차이는 그대로 뒀다** | 띠를 얹으면 "같은 조건에서 만들었다"가 된다 |

**짝이 되는 둘째 조항이 더 중요하다 — 차이는 그대로 둔다.**

인트로에서 클론의 3k–8k 가 원본보다 4.0 dB 적은데 **EQ 로 안 맞췄다.** 원본의 흐림(라플라시안
4.3 대 12.6)과 화면비 차이(원본 2.0:1 · 클론 16:9)도 그대로 둔다. 미술 감독의 근거:

> 띠를 얹는 것은 **「원본과 같은 조건에서 만들었다」고 말하는 것**이 된다.
> 실제로는 다른 조건이었고 그 사실이 화면비에 남아 있다. 가리면 그 사실을 지우는 것이다.

**갈리는 선은 이것이다 — 지금 비교를 위해 정하는 값이면 맞추고,
그때 그 조건에서 나온 것이면 둔다.**

**「우리가 만들었나」가 아니라 「지금 정하는 값인가」다.** 그 차이가 실제로 갈린 자리가 있다.
클론이 16:9 로 꽉 찬 것은 **우리가 그 화면비로 생성했기 때문**이라 "우리가 만든 값"이지만,
그건 **그때의 생성 조건**이지 지금 비교를 위해 정하는 값이 아니다. 그래서 둔다.

**우리가 정한 생성 조건이 결과에 남은 것도 지우지 않는다.**

| | 지금 정하는 값인가 | 결정 |
|---|---|---|
| 칸 크기 · 배율 · 게인 · 라벨 자리 | 그렇다 — 지금 나란히 놓으려고 정한다 | 맞춘다 |
| 원본 음질(고역 4.0 dB)·흐림 | 아니다 — 소재가 원래 그렇다 | 둔다 |
| 클론 화면비 16:9 | 아니다 — **그때의 생성 조건**이다 | 둔다 |

### 규칙을 쓸 때는 이미 내린 결정 **전부**에 대 본다

**이 절이 한 번 틀린 채로 들어갔다.** 처음 문장은 "우리가 넣은 값이면 맞춘다"였는데,
그 문장으로 화면비를 대면 **맞추라고 읽힌다** — 실제 결정은 그대로 두는 것이었다.
사례 셋(칸 크기·게인·얼굴 크기)에서 뽑았고 그 셋은 다 "우리가 정한 값"이라 안 갈렸다.
**넷째 사례가 오자 문장이 깨졌다.**

같은 일이 연출에게도 있었다. 「원문 그대로」 규칙을 v7 씬들로 세 줄로 뽑았는데
v8 에서 넷째 줄이 붙었다 — 세 줄로는 그 씬을 설명하지 못했다.

**규칙을 사례에서 뽑으면 그 사례들이 덮는 데까지만 맞다.**
그래서 규칙 문장을 만들면 **넘기기 전에 이미 내린 결정 전부에 대 본다.**
하나라도 반대로 나오면 문장이 틀린 것이다. **반대로 나온 사례는 문서에 같이 남긴다** —
규칙만 있으면 다음 사람이 또 같은 길로 가고, 반례가 있으면 그 자리에서 막힌다.

**그리고 규칙을 뽑은 사례 목록을 규칙 옆에 적는다.** 위 규칙은 **칸 크기 · 게인 · 라벨 자리**
셋에서 나왔고 화면비에서 깨졌다. 목록이 있으면 다음 사람이 **이 셋이 덮는 데까지만 맞다**는 것을
알고 넷째 사례에서 의심한다. "전부에 대 보라"만 있으면 **무엇에 대 봐야 하는지**를 모른다.

**이 종류는 틀려도 렌더가 안 죽고 결과물을 봐도 안 걸린다.** 문장이 틀린 채로 남아 있으면
다음 편에서 조용히 반대로 간다.

## 상수는 모으고, 유도값은 식으로 둔다

**가르는 기준은 하나다 — 다른 값에서 나오는가.**

```
상수    어디서도 유도되지 않는다. 사람이 정한다
        LEAD 0.5 · GAP 0.8 · CHARS_PER_SEC 8.7 · lineW 2 · pad 56
        → 한 곳에 모은다 (`pipeline/common.py` · `theme.ts` · `grammars.json`)

유도값   다른 값에서 나온다
        카드 안쪽 크기 · 씬 슬롯 · 자막 시각
        → 식으로 둔다. 적어 두면 입력이 바뀔 때 조용히 틀린다
```

**「한 곳에 모으면 안전하다」가 상수에는 맞고 유도값에는 반대다.**
값 하나를 공용으로 만드는 것은 **위험을 한곳에 모으는 것**이고, 식을 공용으로 만드는 것은
다르다 — 입력이 바뀌면 결과가 따라오니 **「틀린 채 굳는」 상태가 안 생긴다.**

**근거** — 카드 안쪽 크기(유도값)를 셋이 각자 계산해서 셋 다 틀렸다.

```
엔지니어   테두리 2px 을 안 빼고 1728×710      계산에서
연출      710 을 계획서에 그대로 옮김          전달에서
미술      y 여백을 30 으로 잡아 761           오기에서
```

**값이 셋 다 달라서 대조하다 걸렸다. 값이 하나였으면 셋 다 같은 값으로 틀렸을 것이고
아무도 몰랐다.** 그래서 **공용화와 「식으로 두는 것」은 같이 가야 한다** — 값만 공용으로
만들면 대조할 상대가 없어진다.

그리고 유도값은 **입력이 자리마다 다르다.** `safeBottom` 이 panel 218 · workshop 232 라
한 숫자로 적으면 **한 문법에서만 맞고 다음 편이 다른 문법이면 조용히 틀린다.**

## 통과 기준은 숫자로 말한다

**"적용했다" "고쳤다" "좋아졌다"는 숫자 없이 하지 않는다.**

| 주장 | 붙여야 할 숫자 |
|---|---|
| 전 씬에 적용 | 해당 데이터가 있는 씬 수 / 전체 |
| 선명해졌다 | 라플라시안 분산 이전 → 이후 |
| 읽힌다 | 대비값, 안전영역 침범 여부 |
| 음성이 맞다 | CER, 그리고 받아쓰기 원문 |
| 문법이 맞다 | `46_grammar_check.py` 종료코드 |

**인코딩 후 파일에서 잰다.** Remotion 스틸은 무손실이라
h264가 어두운 영역에서 만드는 문제를 못 보여준다.


## 첫 시험 — 미술 감독이 v11에서 잡은 것

구조를 만든 직후 미술 감독에게 최종본을 검토시켰다. 총괄이 못 본 것 넷을 잡았다.

| 발견 | 측정 | 판정 |
|---|---|---|
| 강조 낱말이 켜지기 전 안 보인다 (15/15줄, 합계 22.3초) | 미발화 강조 밝기 18/255, 보통 낱말 91–131/255 | **결함** — 고침 |
| 여러 줄 자막의 둘째 줄이 왼쪽에 붙는다 (s11) | 줄2 중심 471, 화면 중심 960 | **결함** — 고침 |
| 강조가 켜질 때 줄이 10px 왼쪽으로 튄다 | 11개 표본 전부 −10px | **결함** — 고침 |
| 자막 밑변이 화면 아래 57px | 유튜브 진행 막대와 겹침 | **결함** — 84px로 올림 |
| `grammars.json` 의 stage·workshop 자막 규격이 안 먹는다 (0/7) | 상자 높이 58px 전 씬 동일 | **설계대로** — 자막층은 편 단위다 |

마지막 하나는 결함이 아니다. 자막 자리가 씬마다 튀면 영상이 망가져 보이므로
자막층·안전영역은 편 단위로 고정된다(`caption.unit: "episode"`).
다만 파일 구조가 오해를 부르는 건 사실이다 — 예외 문법의 자막 규격은 조용히 무시된다.

이 표는 그때의 기록이다. **지금 경계로는 "고침"까지 미술의 일이다** — 위처럼 재서
"무엇이 얼마나 틀렸다"를 낸 다음 그 부품 코드를 직접 고친다.
**바뀐 것은 손이지 검증이 아니다** — 미술이 고친 부품은 미술이 검증하지 않는다.

**얻은 것**: 만든 사람은 자기 코드의 의도를 알기 때문에 결과를 보지 않는다.
`rgba(18,20,26,0.45)` 는 상자 *안에서* 읽히라고 넣은 색인데, 상자가 켜지기 전에도
그 색이라는 걸 만든 사람은 놓쳤다. 검토자는 화면만 보므로 바로 걸렸다.

## 엔지니어를 뒤늦게 넣은 이유

처음 다섯으로 나눌 때 파이프라인 스크립트를 총괄의 예외로 두었다. 그게 틀렸다.

E00 한 편에서 **엔지니어 영역에서만 여섯 건**이 났고, 아무도 검사하지 않았다.

| 어긋난 것 | 어떻게 드러났나 |
|---|---|
| `common.py` 가 소수를 몰라 `0.35초` → `영.삼십오 초` | 사용자가 듣고 발견 |
| 빼기표를 모르고, 숫자 뒤 문장 쉼표를 삼킴 | 위를 고치다 함께 발견 |
| `48_rec_sync.py` 경로 판정 역논리 (`is_absolute()`) | 돌려서야 발견 |
| 저장소에 `grammar.ts` 만 넣고 의존 파일 누락 | 커밋 직전 확인에서 발견 |
| `grammar.ts` ↔ `Stage.tsx` 순환 참조 | 렌더가 죽어서 발견 |
| `--emph-only` 를 잘못된 폴더에서 3회 연속 실패 | `tail` 에 묻혀 한참 뒤 발견 |

공통점은 **조용히 틀린다**는 것이다. 화면은 그럴듯하게 나오고, 스크립트는 종료코드를
삼키고, 부분만 적용된 채로 전체인 줄 안다. 미술 감독이 화면을 보면 잡히지만
배관은 보는 사람이 없으면 끝까지 안 잡힌다.

그래서 엔지니어의 통과 기준은 전부 **"조용히 틀리지 않게"** 로 되어 있다 —
종료코드, 적용 범위 세기, 경로 확인, 저장소 클론 검증, 순환 참조 금지.

### 그중 한 갈래 — 후단이 앞단에서 맞춘 값을 흐트러뜨린다

**앞 단계에서 통과한 것이 뒤 단계에서 무효가 되는데 아무도 안 보는 자리**가 따로 있다.
연출이 이름을 붙였다. 성질이 이렇다.

```
틀려도 렌더가 안 죽는다
결과물을 봐도 안 걸린다          ← 0.6 LU 는 들어서 못 잡는다
앞단 담당은 자기 값이 바뀐 줄 모른다
```

E01 에서 나온 것들이다.

| 앞단이 맞춘 것 | 후단이 한 일 | 어떻게 잡았나 |
|---|---|---|
| 음악이 인트로 두 클립을 **0.3 LU** 로 맞춤 | 마스터 `loudnorm` 한 패스가 **0.6 LU** 로 벌림 | 승인 전에 모의 트랙으로 미리 잼 |
| 음악이 꼬리를 통짜와 **같은 게인**으로 둠(2.6 LU) | 같은 이유로 **3.7 LU** 로 벌림 | 〃 |
| 미술이 씬 좌표를 실측으로 맞춤 | 씬 경계를 **길이로 반올림**해 이음매에 한 프레임 틈 | 중간 삽입을 넣다 걸림 |
| 미술이 배지·윗줄에서 붉은색을 뺌 | 헤드라인 상자가 **`T.fail` 로 남아** 같은 연상이 돌아옴 | 미술이 **360px 축소본**을 보고 잡음 |

**넷째 줄만 값이 아니라 「뜻」이 흐트러진 사례다.** 앞 셋은 숫자로 잡히지만 이것은 안 잡힌다.
그리고 **1280px 로 크게 보면 안 보이고 줄이면 보였다** — 축소본이 원치수보다 잘
잡는 것이 있다. 썸네일은 피드에서 그 크기로 보이므로 `65_render_derived.sh` 가
`thumbs/thumb_<v>_<폭>.png` 를 같이 뽑는다(기본 **168 · 300 · 480**, Lanczos).
**표시 폭은 잰 값이 아니라 가정이라 하나로 두지 않는다**(미술) — 셋 다에서 같은 결론만 쓴다.

**막는 방법은 하나다 — 뒤 단계를 거친 뒤에 앞단의 값을 다시 잰다.**
「승인 2 를 스틸이 아니라 영상으로 본다」로 바뀐 것도 같은 뿌리다.
그리고 **뒤 단계가 아직 없어도 모의로 만들어 미리 잴 수 있다** — 위 둘이 그렇게 잡혔고,
그때 걸리면 17분짜리 렌더를 다시 돌리지 않는다.

### 같은 성질의 갈래 넷

E01 하루에 넷이 나왔다. **넷 다 렌더가 안 죽고 결과물을 봐도 안 걸린다.**

| | 무엇이 일어나나 | 사례 |
|---|---|---|
| 1 | **후단이 앞단의 값을 흐트러뜨린다** | `loudnorm` 한 패스가 음량 관계를 0.3→0.6 LU 로 벌림 |
| 2 | **정리가 흐트러뜨린다** | 흩어진 테두리를 토큰으로 묶다 1px 자리를 2px 로 바꿀 뻔 |
| 3 | **식이 좁아 입력을 안 따라간다** | `panelInner` 가 `contain` 을 안 봐서 상자 없는 문법에서 24.3% 를 흘림 |
| 4 | **「무해하다」고 넘긴 것이 남의 설계에 들어간다** | `spring` 끝값 0.4% 를 「작다」고 넘겼더니 밑줄이 5px 짧았다 |
| 5 | **검사가 자기 입력을 검사한다** | 대본을 고쳤는데 옛 음성이 CER 0.000 으로 통과 — 검사가 옛 사본을 봤다 |

**1~3 은 모르고 틀린 것이고 4 는 알고도 작다고 넘긴 것이다.** 그래서 4 가 따로다.

**5 는 검사 자체가 눈이 먼 것이다.** `30_nar_check` 는 `tts_input` 과 받아쓰기를 대조하는데
**둘 다 옛것이면 서로 맞는다** — 앞단이 움직이면 검사도 같이 움직인다.
잡은 것은 자막이었고, **이 공정에서 대본과 직접 대조하는 자리가 거기뿐이었다.**
막는 방법은 **입력의 판본을 산출물에 박아 두는 것**이다(`10` 이 씬별 대본 지문을 남기고
`30`·`40` 이 대조한다). 검사를 하나 더 만드는 것으로는 안 된다 — 새 검사도 같은 사본을 본다.

**4 의 값은 「5px 를 찾았다」가 아니다.** 그 0.4% 를 「그런 자리는 이렇게 피하세요」로
**넘겼더니 받는 쪽이 그 전제로 설계를 쌓았다** — 연출이 시간축에 `linear` 를 네 자리
박았고, 고치고 나니 그중 셋이 필요 없었다.

```
넘기면   받는 쪽이 그 전제로 설계한다. 전제가 틀리면 설계도 틀린다
고치면   아무도 그 전제를 알 필요가 없다
```

**작아서 안 고칠 것이면 넘기지도 마라.** 넘기는 순간 그것은 남의 설계에 들어간다.

## 한 항목이 아직이라고 검수 전체를 미루지 않는다

그 항목만 판정에서 빼고 **나머지를 보게 한다.**

E01 에서 BGM 하나를 기다리느라 화면·문구·끝맺음 검수가 **다섯 판** 같이 미뤄졌다.
그 사이 사용자가 직접 결함을 찾았고 **「전체를 검수하는 사람이 없나」**고 물었다.

**미루는 것이 순환일 때가 있다.** E01 의 s30 끝 화면은 **편집자 판정이 있어야 값이 나오는데
편집자는 마스터가 있어야 본다.** 그 하나를 기다리면 마스터가 안 나오고 판정도 안 나온다.

그리고 **사용자 요청은 기억으로 관리하지 않는다** — `script/requests.json` 에 적고
**「들어감」과 「재서 확인됨」을 가른다.** 앞엣것은 코드에 넣은 것이고 뒤엣것은
**그 마스터에서 재 본 것**이다. E01 에서 「들어감」 열셋 중 여덟이 **마스터에서 안 본 것**이었고,
그 칸이 없었으면 열셋이 다 초록으로 보였을 것이다.

## 규칙을 적을 때 「지금 몇 곳」을 같이 적는다

**규칙만 적으면 쓴 사람도 어긴다.** E01 에서 셋이 같은 자리에서 넘어졌다 —
미술이 「값을 고칠 때 몇 곳에 있는지부터 세라」를 적고 **5분 뒤** 한 곳만 고쳤고(넷이었다),
총괄이 「한 항목 때문에 검수를 미루지 않는다」를 넣고 **한 시간 뒤** 하나로 여덟을 세웠다.
**잊은 것이 아니다. 쓴 지 5분·한 시간이다.** 그러면 사람이 아니라 **규칙의 꼴**을 고칠 일이다.

**셀 수 있는 규칙과 못 세는 규칙을 가른다.**
```
셀 수 있으면   **검사가 그 수를 찍는다.** 규칙 옆에 수를 적지 않는다 —
              적어 두면 그 수가 낡는다(E01 에서 낡은 목록이 넷이었다)
못 세면       **「기계가 못 셈」이라고 적는다.** 억지 수를 붙이면
              「안 재고 100 이라고 적은」 자리가 된다
```
**규칙마다 「이건 검사가 세나」를 먼저 적는다.** 그 한 줄이 없으면 다음 사람이 세야 하는지도 모른다.
