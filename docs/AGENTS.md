# 다섯 사람으로 나눈 이유

한 에이전트가 대본·화면·소리·검사를 다 하면 **만든 사람이 자기 것을 검사하게 된다.**
그러면 같은 실수가 반복된다. E00 한 편에서 실제로 이렇게 났다.

| 어긋난 것 | 잡았어야 할 사람 | 왜 못 잡았나 |
|---|---|---|
| 노래방 자막이 5/24 씬만 도는데 "전 씬 적용" | 소리 | 만든 사람이 세지 않고 보고 |
| 참고 영상의 격자·레이저·팔레트를 그대로 옮김 | 미술 | 참고를 *재는 것*과 *옮기는 것*을 안 나눔 |
| 훅에서 예제를 어둡게 깔아 선명도 233→6.6 | 연출 | 그 씬의 일(증거 제시)을 놓침 |
| 소수점 읽기 결함 (`0.35초` → `영.삼십오 초`) | 소리 | CER만 보고 듣지 않음 |
| 바탕 결이 화질 저하로 보임 | 미술 | 인코딩 **후**를 안 봄 |
| 강조 낱말이 상자 두 개로 쪼개짐 | 미술 | 렌더 후 확인 안 함 |
| 계획서와 실물 불일치 (s14, 카드 어휘) | 총괄 | 문서 갱신이 만든 사람 몫이었음 |
| 창 테두리 2px 을 칸에서 흘려 이미지가 창 밖으로 밀림 | 미술 | 총괄이 직접 만들었다 |
| "이전과 같다" 오보고 — 상관 0.9987 은 고친 코드끼리 비교한 값 | 미술 | 만든 사람이 검증을 짰다 |

앞의 일곱 건 중 여섯 건을 **사용자가 먼저 발견했다.** 그게 이 구조를 만드는 이유다.
뒤의 두 건은 구조를 만든 **뒤에** 났다. 총괄이 규칙을 어기고 직접 만들었기 때문이다.

## 다섯 사람

| 사람 | 쓰는 파일 | 넘기는 것 |
|---|---|---|
| **시나리오 작가** `screenwriter` | `script/script_v1.md` `scenes_v1.json` `chapters.json` | 대본 → 연출, 읽을 문장 → 소리 |
| **연출 감독** `director` | `visual_plan.md` `grammar.json` `visual_prep.json` | 화면 계획 → 미술, 씬 배정 → 엔지니어 |
| **미술 감독** `art-director` | `grammars.json` `theme.ts` 의 **값**, `public/<slug>/*` | 부품 요구사항 → 엔지니어, 소재 → 연출 |
| **음악 감독** `sound-director` | `voice.json` `tts_overrides.json` `audio/*` `captions.json` `scenes_v2.json` | 시각표 → 연출·미술, 스크립트 결함 → 엔지니어 |
| **엔지니어** `engineer` | `pipeline/*` `src/**/*.tsx` `grammar.ts` `.claude/agents/*` `README.md`, 그리고 **서버·연결·설치·환경 전부** | 도구 → 전원 |
| **총괄** (지금 이 세션) | 없음 — **만들지 않는다. 규칙이다** | 배분·관문·보고 대조·사용자 응대 |

**경계는 산출물로 긋는다.** 남의 파일을 고치지 않는다. 필요하면 요청한다.
이게 지켜지지 않으면 누가 무엇을 깨뜨렸는지 추적할 수 없다.

## 역할은 정하고 판단한다. 엔지니어가 만든다

여섯 역할 전부 같은 규칙이다. **선 긋는 기준은 "판단인가 구현인가"다.**
연출이 "s06 은 표 말고 목록"이라고 정하는 것은 **판단**,
그것을 `scenes.tsx` 에 쓰는 것은 **구현**이다.
판단은 그 역할이 하고, 구현은 엔지니어가 한다.

| 역할 | 자기가 하는 것 | 엔지니어에게 넘기는 것 |
|---|---|---|
| 시나리오 작가 | 대본 텍스트, 씬 분할, 강조 표시 | 대본을 데이터로 바꾸는 스크립트 |
| 연출 감독 | 문법 선택, 씬별 카드, 예외, 리듬 판단 | `scenes.tsx` 코드 |
| 미술 감독 | 미술적 요구사항, 화면 문제 정리 | 부품 코드, 소재 생성 스크립트 |
| 음악 감독 | 읽기 사전, 음성·자막 판단, 음량 기준 | TTS·자막 빌드 스크립트 |
| 총괄 | 일 나누기, 보고 대조, 사용자 보고 | 전부 |
| 엔지니어 | 위 전부의 구현 | — |

사람이 하는 일도 같다. 미술 감독이 렌더러 소스를 고치지 않고,
작가가 대본 변환기를 고치지 않는다.

### 예외 — 자기 영역의 창작물 자체는 그 역할이 직접 쓴다

대본 텍스트(`script_v1.md`), 읽기 사전(`tts_overrides.json`),
문법 값(`grammars.json`), 테마 토큰(`theme.ts`) 이 그렇다.
그건 **남의 요구사항을 구현하는 것이 아니라 그 사람의 결과물**이다.
작가에게 대본을 엔지니어가 써 주는 것은 말이 안 된다.

가르는 법: **그 파일의 내용이 그 역할의 판단 그 자체면 직접 쓴다.**
판단을 화면에 옮기기 위한 코드면 넘긴다.
`theme.ts` 의 색값은 미술의 판단이고, 그 색을 읽어 그리는 `Stage.tsx` 는 구현이다.

### 돌리는 것과 고치는 것은 다르다

담당은 자기 단계의 스크립트를 **돌린다.** 소리가 `20_tts_generate.py` 를 돌리는 것은 소리 일이다.
그 스크립트가 **틀렸을 때 코드를 고치는 것**이 엔지니어 일이다.
넘기는 것은 실행이 아니라 수정이다.

### 렌더는 여기서 갈린다

| 무엇 | 누구 |
|---|---|
| 렌더 **결과** — 그림이 어떤가, 읽히는가, 어긋나는가 | 미술 감독 |
| 렌더의 **에러·속도·실패** | 엔지니어 |
| 렌더를 돌리기 위한 **코드·설정·실행** | 엔지니어 |

미술은 **미술적 요구사항과 문제를 정리하는 데까지**다.

실제로 총괄이 미술 감독에게 부품 검토를 시키면서
"고치세요, `tsc` 통과 확인하세요"라고 **코드 수정까지** 맡긴 적이 있다.
새 경계로는 잘못된 지시다. 미술이 낼 것은
"창 안쪽 칸에서 테두리 2px 이 안 빠졌다. 이미지가 창 밖으로 2px 밀린다"까지고,
코드를 고치고 `tsc` 를 돌리는 것은 엔지니어다.

### 서버·연결·환경은 엔지니어 것이다

산출물로 경계를 그으면 **인프라가 아무의 것도 아닌 것처럼 보인다.** 그래서 각자 판다.

| 무엇 | 누구 |
|---|---|
| 서버·네트워크·연결·포트·방화벽 | 엔지니어 |
| 설치, 환경 변수, 자격 증명, 경로 설정 | 엔지니어 |
| 그 위에서 **무엇을 만들지** | 그 담당 |

**어느 역할이든 "붙으려는데 안 붙는다"에 부딪히면 거기서 멈추고 엔지니어에게 요청한다.**
스스로 진단하지 않는다. 포트를 훑거나 프로세스를 뒤지거나 다른 곳의 주소를 역추적하지 않는다.

요청에는 **진단이 아니라 증상**을 싣는다.

```
어느 주소로 무엇을 하려 했나      http://127.0.0.1:8188 에 20_tts_generate
무슨 응답을 받았나                연결 거부 (타임아웃 3초)
어느 설정의 어느 값을 보고 있었나  pipeline/voice.json 의 providers.comfyui_chatterbox.hosts
어느 단계에서 멈췄나              2단계 음성, 씬 0/24
```

**총괄도 예외가 아니다.** 총괄은 읽고 판단하고 배분한다.
연결 확인 명령을 직접 돌리지 않는다 — 그것도 만드는 일이다.

반대 방향도 같다. **엔지니어는 인프라를 고치되 그 위에서 무엇을 만들지는 판정하지 않는다.**
`voice.json` 은 음악 감독의 파일이지만 그 안에서 경계가 키로 갈린다. 한 파일에서 그런 유일한 자리다.

**가르는 기준은 하나다 — 그 값이 소리를 바꾸는가.**

| | 키 | 누구 |
|---|---|---|
| 소리를 **안** 바꾼다 | `hosts` `host` `max_queue` `parallel` `timeout_sec` — 어느 서버에서 도느냐만 정한다 | 엔지니어 |
| 소리를 **바꾼다** | `provider` `ref_file` `exaggeration` `cfg_weight` `temperature` `seed` — 하나만 건드려도 목소리가 달라진다 | 음악 감독 |

같은 참조·파라미터·시드면 서버가 바뀌어도 같은 소리가 난다. **잠금의 대상은 아래 줄이고 위 줄은 잠글 이유가 없다.**
서버가 두 대로 늘어 `parallel` 을 켜는 것은 음악 감독의 일이 아니다.

실제로 이렇게 났다. 음악 감독이 ComfyUI 에 붙으려다 서버가 안 잡히자,
**총괄이 직접** TCP 를 열고 `/system_stats` 와 `/queue` 를 던져 진단했고,
**음악 감독은** `lsof` 로 포트 소켓을 훑어 다른 프로그램의 연결에서 서버 주소를 역추적했다.
둘 다 결과는 맞았다. **경로가 틀렸다.** 다음에 같은 자리가 방화벽·포트 변경·모델 미설치로
막히면 음악 감독은 풀 수 없고, 그때는 시간만 버린다.

### 요구사항이 옳은지는 엔지니어가 판단하지 않는다

엔지니어는 받은 요구사항을 구현하고, 그것이 미술적·연출적으로 옳은지는 판단하지 않는다.
"이 색이 별로다"는 엔지니어의 말이 아니다. 엔지니어가 되묻는 것은 둘뿐이다 —
**구현할 수 없는가, 다른 것과 충돌하는가.** 그때도 대안을 정하지 않고 담당에게 되돌린다.
반대로 담당은 "이 코드를 이렇게 짜라"고 말하지 않는다. 무엇이 필요한지까지 말한다.

## 총괄이 하는 일

### 규칙 — 총괄은 직접 일을 하지 않는다

**예외가 없다.** 이 구조를 만든 이유가 "만든 사람이 자기 것을 검사했다"이므로,
총괄이 직접 만들면 검사할 사람이 다시 사라진다.

**하지 않는 것**

- 파일을 만들거나 고치지 않는다 — 대본·화면·부품·소리·스크립트·문서 전부
- 서체·색·수치를 직접 정하지 않는다
- 문서를 직접 정리하지 않는다. 문서에도 담당이 있다
- "한 줄이니까" "급하니까"를 예외로 삼지 않는다. 아래 사건이 2px 짜리였다

**하는 것 — 네 가지**

1. **일을 나눈다** — 어느 산출물인지 보고 담당을 정한다
2. **검토를 다른 담당에게 맡긴다** — 만든 담당은 자기 것을 검토하지 않는다
3. **두 보고를 대조한다** — 만든 쪽의 숫자와 검토한 쪽의 숫자가 어긋나면 그게 결함이다
4. **사용자에게 보고한다** — 무엇이 됐고 무엇이 안 됐는지, 숫자와 함께

### 누구 일인지 모르면 — 사용자에게 승인을 요청한다

**총괄이 처리하지 않는다.** 담당이 애매한 일을 총괄이 떠맡는 것이
이 구조가 무너지는 경로다. 산출물 표에서 담당이 안 나오면 이렇게 한다.

```
"이 일은 <담당>의 것으로 보입니다. 그 담당에게 시킬까요?"
→ 사용자의 답을 기다린다. 기다리는 동안 손대지 않는다
```

새 종류의 산출물이 생겨서 표에 없는 것이면, 표를 고칠 담당(엔지니어)에게
시킬지도 함께 묻는다. 총괄이 표를 고치지 않는다.

처음에는 "파이프라인 스크립트만은 총괄이 손댄다"고 예외를 두었는데, 그게 구멍이었다.
25개 스크립트 1500줄과 조립 계층은 그 자체로 엔지니어링이고,
이번 편에서 여기서만 여섯 건이 났는데 아무도 검사하지 않았다. **엔지니어가 맡는다.**

## 한 편의 흐름

```
1  주제        작가 →  총괄 관문: 채택 기준 3줄이 다 참인가
2  대본        작가 →  소리가 검토(읽히는가) → 총괄 관문
3  음성        소리 →  30_nar_check + 받아쓰기 눈으로 읽기 → 총괄 관문
4  시각표      소리 →  40_nar_finalize. 여기서 편 길이가 확정된다
5  화면 계획   연출 →  작가가 검토(주장을 증명하는가) → 46_grammar_check
6  부품·소재   미술이 요구·소재 → 엔지니어가 부품 구현 → 연출이 검토(그 씬의 일을 하는가)
7  씬 배정     연출이 계획서 → 엔지니어가 scenes.tsx → 미술이 검토(문법이 담을 수 있는가)
8  자막        소리 →  50_captions_build. 적용 범위를 센다
9  첫 렌더     엔지니어 → 연출·미술이 인코딩 후 파일에서 검토  ← 사용자 승인
10 파생·업로드 엔지니어 → 사용자가 직접 올린다
```

렌더·파생도 총괄이 돌리지 않는다. `60_render_master.sh` `65_render_derived.sh` 는
엔지니어의 스크립트다. 총괄은 **관문**(총괄 관문이라고 적힌 줄)에만 선다.

**3번과 4번 사이가 되돌릴 수 없는 지점이다.** 시각표가 확정되면 화면이 그 위에 얹힌다.
대본을 고치려면 3번으로 돌아가야 하고, 음성을 다시 만들어야 한다.

## 교차 검토 규칙

**인접한 쪽끼리만 본다.** 전원이 전원을 보면 비용만 든다.

```
작가 ←→ 연출        대본의 주장 ↔ 그것을 증명하는 화면
연출 ←→ 미술        필요한 것 ↔ 담을 수 있는 것
작가 ←→ 소리        쓴 문장 ↔ 실제로 읽히는 소리
엔지니어 ←→ 전원    만든 도구 ↔ 그 담당이 실제로 쓸 수 있는가
```

엔지니어만 전원과 맞닿는다. 도구는 모두가 쓰기 때문이다.
다만 검토 방향은 한쪽이다 — 담당은 **도구가 쓸 만한가**를 보고,
엔지니어는 **검사 기준의 숫자**를 혼자 정하지 않는다.
요구사항은 담당 → 엔지니어 한 방향으로 흐른다.
엔지니어는 그 요구사항이 미술적·연출적으로 옳은지 되묻지 않고,
담당은 구현 방법을 지시하지 않는다.

검토는 **한 가지만** 본다. 취향을 말하지 않는다.
- 작가가 연출을 볼 때: 이 화면이 그 씬의 주장을 증명하는가
- 연출이 미술을 볼 때: 이 화면이 그 씬의 일을 하는가
- 미술이 연출을 볼 때: 이 문법이 그 카드를 담을 수 있는가
- 소리가 작가를 볼 때: 이 문장이 실제로 읽히는가

## 검증은 바뀌기 전 산출물과 대조한다

구조를 만든 다음 날, 총괄이 미술 영역인 화면 부품(`remotion/src/knowhow/Workshop.tsx`
의 창 안쪽 칸 계산)을 직접 만들었다. 창 테두리 2px 을 칸에서 빼지 않아 이미지가
가로세로 각각 2px 씩 크게 그려졌다. 창 밖으로 밀렸고, 이미지 퍼센트로 찍은
주석 상자도 그만큼 어긋났다.

더 나쁜 것은 **"이전과 같다"고 보고한 것**이다. 근거로 댄 상관 0.9987 은
**고친 코드끼리** 비교한 값이었다. 이전 마스터와 대조하니 0.85 였다.
만든 사람이 검증을 짜니, 검증이 자기 가정을 확인하는 방향으로만 짜였다.

**같은 날 총괄은 서체 수정과 문서 정리도 혼자 했다.** 규칙이 필요한 이유가 이것이다.

| | |
|---|---|
| 무엇과 대조하나 | **바뀌기 전 산출물** — 이전 마스터 mp4, 이전 스틸, 이전 JSON |
| 언제 떠 두나 | **고치기 전에.** 고친 뒤에는 이전 것이 남아 있지 않다 |
| 누가 재나 | **만든 담당이 아닌 다른 담당** |

고친 코드끼리 비교한 값은 검증이 아니라 **재현**이다.
두 판본이 같은 실수를 공유하면 숫자는 1.0 에 가깝게 나온다.
"이전과 같다"고 말하려면 이전 것이 **파일로** 남아 있어야 한다. 없으면 그 주장을 하지 않는다.

검토자는 만든 사람의 검증 절차를 물려받지 않는다. **무엇과 대조할지 스스로 정한다.**
만든 사람이 "이 스크립트로 재면 됩니다"라고 건네는 것을 그대로 돌리면 같은 구멍에 빠진다.

## 크기는 중립, 판정은 색 — 그리고 차이는 그대로 둔다

연출과 음악 감독이 각자 실측으로 같은 자리에 닿았다. 화면과 소리를 넘나드는 규칙이라 여기 둔다.

```
화면    크기는 중립, 판정은 색
소리    음량은 중립, 차이는 그대로
```

**둘을 나란히 놓고 보이는 편에서는 크기·음량이 판정으로 읽힌다.** 큰 쪽이 옳은 쪽이고,
큰 소리가 진짜다. 그래서 **비교의 축이 아닌 것은 맞춰 놓고, 판정은 색이나 라벨처럼
읽는 사람이 판정으로 알아보는 장치로만 한다.**

| 누가 | 무엇을 했나 | 왜 |
|---|---|---|
| 연출 | s05 의 두 조건 칸을 **238 대 237** 로 맞췄다 | 큰 쪽이 옳은 쪽으로 읽히고 있었다 |
| 음악 | 인트로 원본·클론의 **4.6 LU 차이를 없앴다** | 큰 쪽이 「더 진짜」로 읽힌다 |
| 음악 | s18 꼬리를 **통짜와 같은 게인**으로 뒀다 | 2.3 dB 크면 「상기」가 「강조」가 된다 |
| 엔지니어 | 썸네일 두 칸의 **얼굴 크기**를 502 대 500 으로 맞췄다 | 배율을 묶었더니 얼굴이 1.6배 차이로 남았다 |
| 연출·미술 | 인트로에서 원본·클론의 **화면비 차이는 그대로 뒀다** | 띠를 얹으면 "같은 조건에서 만들었다"가 된다 |

**짝이 되는 둘째 조항이 더 중요하다 — 차이는 그대로 둔다.**

인트로에서 클론의 3k–8k 가 원본보다 4.0 dB 적은데 **EQ 로 안 맞췄다.** 원본의 흐림(라플라시안
4.3 대 12.6)과 화면비 차이(원본 2.0:1 · 클론 16:9)도 그대로 둔다. 미술 감독의 근거:

> 띠를 얹는 것은 **「원본과 같은 조건에서 만들었다」고 말하는 것**이 된다.
> 실제로는 다른 조건이었고 그 사실이 화면비에 남아 있다. 가리면 그 사실을 지우는 것이다.

**갈리는 선은 이것이다 — 지금 비교를 위해 정하는 값이면 맞추고,
그때 그 조건에서 나온 것이면 둔다.**

**「우리가 만들었나」가 아니라 「지금 정하는 값인가」다.** 그 차이가 실제로 갈린 자리가 있다.
클론이 16:9 로 꽉 찬 것은 **우리가 그 화면비로 생성했기 때문**이라 "우리가 만든 값"이지만,
그건 **그때의 생성 조건**이지 지금 비교를 위해 정하는 값이 아니다. 그래서 둔다.

**우리가 정한 생성 조건이 결과에 남은 것도 지우지 않는다.**

| | 지금 정하는 값인가 | 결정 |
|---|---|---|
| 칸 크기 · 배율 · 게인 · 라벨 자리 | 그렇다 — 지금 나란히 놓으려고 정한다 | 맞춘다 |
| 원본 음질(고역 4.0 dB)·흐림 | 아니다 — 소재가 원래 그렇다 | 둔다 |
| 클론 화면비 16:9 | 아니다 — **그때의 생성 조건**이다 | 둔다 |

### 규칙을 쓸 때는 이미 내린 결정 **전부**에 대 본다

**이 절이 한 번 틀린 채로 들어갔다.** 처음 문장은 "우리가 넣은 값이면 맞춘다"였는데,
그 문장으로 화면비를 대면 **맞추라고 읽힌다** — 실제 결정은 그대로 두는 것이었다.
사례 셋(칸 크기·게인·얼굴 크기)에서 뽑았고 그 셋은 다 "우리가 정한 값"이라 안 갈렸다.
**넷째 사례가 오자 문장이 깨졌다.**

같은 일이 연출에게도 있었다. 「원문 그대로」 규칙을 v7 씬들로 세 줄로 뽑았는데
v8 에서 넷째 줄이 붙었다 — 세 줄로는 그 씬을 설명하지 못했다.

**규칙을 사례에서 뽑으면 그 사례들이 덮는 데까지만 맞다.**
그래서 규칙 문장을 만들면 **넘기기 전에 이미 내린 결정 전부에 대 본다.**
하나라도 반대로 나오면 문장이 틀린 것이다. **반대로 나온 사례는 문서에 같이 남긴다** —
규칙만 있으면 다음 사람이 또 같은 길로 가고, 반례가 있으면 그 자리에서 막힌다.

**그리고 규칙을 뽑은 사례 목록을 규칙 옆에 적는다.** 위 규칙은 **칸 크기 · 게인 · 라벨 자리**
셋에서 나왔고 화면비에서 깨졌다. 목록이 있으면 다음 사람이 **이 셋이 덮는 데까지만 맞다**는 것을
알고 넷째 사례에서 의심한다. "전부에 대 보라"만 있으면 **무엇에 대 봐야 하는지**를 모른다.

**이 종류는 틀려도 렌더가 안 죽고 결과물을 봐도 안 걸린다.** 문장이 틀린 채로 남아 있으면
다음 편에서 조용히 반대로 간다.

## 상수는 모으고, 유도값은 식으로 둔다

**가르는 기준은 하나다 — 다른 값에서 나오는가.**

```
상수    어디서도 유도되지 않는다. 사람이 정한다
        LEAD 0.5 · GAP 0.8 · CHARS_PER_SEC 8.7 · lineW 2 · pad 56
        → 한 곳에 모은다 (`pipeline/common.py` · `theme.ts` · `grammars.json`)

유도값   다른 값에서 나온다
        카드 안쪽 크기 · 씬 슬롯 · 자막 시각
        → 식으로 둔다. 적어 두면 입력이 바뀔 때 조용히 틀린다
```

**「한 곳에 모으면 안전하다」가 상수에는 맞고 유도값에는 반대다.**
값 하나를 공용으로 만드는 것은 **위험을 한곳에 모으는 것**이고, 식을 공용으로 만드는 것은
다르다 — 입력이 바뀌면 결과가 따라오니 **「틀린 채 굳는」 상태가 안 생긴다.**

**근거** — 카드 안쪽 크기(유도값)를 셋이 각자 계산해서 셋 다 틀렸다.

```
엔지니어   테두리 2px 을 안 빼고 1728×710      계산에서
연출      710 을 계획서에 그대로 옮김          전달에서
미술      y 여백을 30 으로 잡아 761           오기에서
```

**값이 셋 다 달라서 대조하다 걸렸다. 값이 하나였으면 셋 다 같은 값으로 틀렸을 것이고
아무도 몰랐다.** 그래서 **공용화와 「식으로 두는 것」은 같이 가야 한다** — 값만 공용으로
만들면 대조할 상대가 없어진다.

그리고 유도값은 **입력이 자리마다 다르다.** `safeBottom` 이 panel 218 · workshop 232 라
한 숫자로 적으면 **한 문법에서만 맞고 다음 편이 다른 문법이면 조용히 틀린다.**

## 담당끼리 직접 주고받는다 — 총괄을 거치지 않는다

**총괄이 중계하면 왕복이 두 배가 되고 옮기다 틀린다.**

E01 하루에 **메시지 교차가 열 번 넘게 났고**, 그중 여럿이 「직접 못 보내서 총괄을 거쳤고
그러는 사이 상대가 이미 답한」 경우였다. 미술이 도식 값을 엔지니어에게 못 보내 총괄에게
돌아왔고, 작가가 음악 감독에게 못 보내 총괄이 옮겼으며, **그 사이 총괄이 옮겨 적으면서
틀린 적도 있다.**

### 근본은 정의 파일의 `tools:` 다

**`.claude/agents/*.md` 의 `tools:` 를 열거형으로 쓰면 거기 적힌 것만 쓸 수 있다.**
안 적으면 전부 상속한다. 그래서 정의 파일에 **`SendMessage` 와 `ListAgents` 를 넣는다.**

```
tools: Read, Write, Edit, Bash, Grep, Glob, SendMessage, ListAgents
```

**`ListAgents` 가 있으면 주소록을 뿌릴 필요가 없다.** 아래 「주소록을 뿌린다」는
**그것이 빠졌을 때의 대응**이다 — 둘을 갈라 둔다. 안 그러면 다음 사람이
`ListAgents` 를 넣어 놓고도 주소록을 뿌린다.

### (대응) 담당을 부르면 총괄이 그 자리에서 전원에게 주소록을 뿌린다

**`ListAgents` 가 정의에 없으면** 이름을 알 방법이 그것뿐이다.
실제로 미술이 엔지니어에게 `engineer` · `engineer-e01` 로 보내려다 실패했고,
작가도 `sound-director` · `engineer` 로 같은 자리를 밟았다.

### 담당 이름을 **역할로** 짓는다

`eng-parser-fix` · `art-template-review` 는 **처음 시킨 일에서 온 이름**이라
역할로 짐작하면 빗나간다. 다음부터는 역할 이름으로 부른다.

### 무엇을 직접, 무엇을 총괄로

```
직접    판단 · 값 · 확인 · 정정 전부
총괄로  판단이 갈려 못 정할 때 · 사용자 승인이 필요할 때 · 결과 보고
```

## 통과 기준은 숫자로 말한다

**"적용했다" "고쳤다" "좋아졌다"는 숫자 없이 하지 않는다.**

| 주장 | 붙여야 할 숫자 |
|---|---|
| 전 씬에 적용 | 해당 데이터가 있는 씬 수 / 전체 |
| 선명해졌다 | 라플라시안 분산 이전 → 이후 |
| 읽힌다 | 대비값, 안전영역 침범 여부 |
| 음성이 맞다 | CER, 그리고 받아쓰기 원문 |
| 문법이 맞다 | `46_grammar_check.py` 종료코드 |

**인코딩 후 파일에서 잰다.** Remotion 스틸은 무손실이라
h264가 어두운 영역에서 만드는 문제를 못 보여준다.

## 첫 시험 — 미술 감독이 v11에서 잡은 것

구조를 만든 직후 미술 감독에게 최종본을 검토시켰다. 총괄이 못 본 것 넷을 잡았다.

| 발견 | 측정 | 판정 |
|---|---|---|
| 강조 낱말이 켜지기 전 안 보인다 (15/15줄, 합계 22.3초) | 미발화 강조 밝기 18/255, 보통 낱말 91–131/255 | **결함** — 고침 |
| 여러 줄 자막의 둘째 줄이 왼쪽에 붙는다 (s11) | 줄2 중심 471, 화면 중심 960 | **결함** — 고침 |
| 강조가 켜질 때 줄이 10px 왼쪽으로 튄다 | 11개 표본 전부 −10px | **결함** — 고침 |
| 자막 밑변이 화면 아래 57px | 유튜브 진행 막대와 겹침 | **결함** — 84px로 올림 |
| `grammars.json` 의 stage·workshop 자막 규격이 안 먹는다 (0/7) | 상자 높이 58px 전 씬 동일 | **설계대로** — 자막층은 편 단위다 |

마지막 하나는 결함이 아니다. 자막 자리가 씬마다 튀면 영상이 망가져 보이므로
자막층·안전영역은 편 단위로 고정된다(`caption.unit: "episode"`).
다만 파일 구조가 오해를 부르는 건 사실이다 — 예외 문법의 자막 규격은 조용히 무시된다.

이 표는 그때의 기록이다. **지금 경계로는 "고침"이 미술의 일이 아니다** —
미술은 위처럼 재서 "무엇이 얼마나 틀렸다"까지 내고, 코드 수정은 엔지니어가 한다.

**얻은 것**: 만든 사람은 자기 코드의 의도를 알기 때문에 결과를 보지 않는다.
`rgba(18,20,26,0.45)` 는 상자 *안에서* 읽히라고 넣은 색인데, 상자가 켜지기 전에도
그 색이라는 걸 만든 사람은 놓쳤다. 검토자는 화면만 보므로 바로 걸렸다.

| `--emph-only` 를 잘못된 폴더에서 3회 연속 실패 | `tail` 에 묻혀 한참 뒤 발견 |

공통점은 **조용히 틀린다**는 것이다. 화면은 그럴듯하게 나오고, 스크립트는 종료코드를
삼키고, 부분만 적용된 채로 전체인 줄 안다. 미술 감독이 화면을 보면 잡히지만
배관은 보는 사람이 없으면 끝까지 안 잡힌다.

그래서 엔지니어의 통과 기준은 전부 **"조용히 틀리지 않게"** 로 되어 있다 —
종료코드, 적용 범위 세기, 경로 확인, 저장소 클론 검증, 순환 참조 금지.

### 그중 한 갈래 — 후단이 앞단에서 맞춘 값을 흐트러뜨린다

**앞 단계에서 통과한 것이 뒤 단계에서 무효가 되는데 아무도 안 보는 자리**가 따로 있다.
연출이 이름을 붙였다. 성질이 이렇다.

```
틀려도 렌더가 안 죽는다
결과물을 봐도 안 걸린다          ← 0.6 LU 는 들어서 못 잡는다
앞단 담당은 자기 값이 바뀐 줄 모른다
```

E01 에서 나온 것들이다.

| 앞단이 맞춘 것 | 후단이 한 일 | 어떻게 잡았나 |
|---|---|---|
| 음악이 인트로 두 클립을 **0.3 LU** 로 맞춤 | 마스터 `loudnorm` 한 패스가 **0.6 LU** 로 벌림 | 승인 전에 모의 트랙으로 미리 잼 |
| 음악이 꼬리를 통짜와 **같은 게인**으로 둠(2.6 LU) | 같은 이유로 **3.7 LU** 로 벌림 | 〃 |
| 미술이 씬 좌표를 실측으로 맞춤 | 씬 경계를 **길이로 반올림**해 이음매에 한 프레임 틈 | 중간 삽입을 넣다 걸림 |
| 미술이 배지·윗줄에서 붉은색을 뺌 | 헤드라인 상자가 **`T.fail` 로 남아** 같은 연상이 돌아옴 | 미술이 **360px 축소본**을 보고 잡음 |

**넷째 줄만 값이 아니라 「뜻」이 흐트러진 사례다.** 앞 셋은 숫자로 잡히지만 이것은 안 잡힌다.
그리고 **1280px 로 크게 보면 안 보이고 360px 로 줄이면 보였다** — 축소본이 원치수보다 잘
잡는 것이 있다. 썸네일은 피드에서 그 크기로 보이므로 `65_render_derived.sh` 가
`thumbs/thumb_<v>_360.png` 를 같이 뽑는다.

**막는 방법은 하나다 — 뒤 단계를 거친 뒤에 앞단의 값을 다시 잰다.**
「승인 2 를 스틸이 아니라 영상으로 본다」로 바뀐 것도 같은 뿌리다.
그리고 **뒤 단계가 아직 없어도 모의로 만들어 미리 잴 수 있다** — 위 둘이 그렇게 잡혔고,
그때 걸리면 17분짜리 렌더를 다시 돌리지 않는다.

### 같은 성질의 갈래 넷

E01 하루에 넷이 나왔다. **넷 다 렌더가 안 죽고 결과물을 봐도 안 걸린다.**

| | 무엇이 일어나나 | 사례 |
|---|---|---|
| 1 | **후단이 앞단의 값을 흐트러뜨린다** | `loudnorm` 한 패스가 음량 관계를 0.3→0.6 LU 로 벌림 |
| 2 | **정리가 흐트러뜨린다** | 흩어진 테두리를 토큰으로 묶다 1px 자리를 2px 로 바꿀 뻔 |
| 3 | **식이 좁아 입력을 안 따라간다** | `panelInner` 가 `contain` 을 안 봐서 상자 없는 문법에서 24.3% 를 흘림 |
| 4 | **「무해하다」고 넘긴 것이 남의 설계에 들어간다** | `spring` 끝값 0.4% 를 「작다」고 넘겼더니 밑줄이 5px 짧았다 |
| 5 | **검사가 자기 입력을 검사한다** | 대본을 고쳤는데 옛 음성이 CER 0.000 으로 통과 — 검사가 옛 사본을 봤다 |

**1~3 은 모르고 틀린 것이고 4 는 알고도 작다고 넘긴 것이다.** 그래서 4 가 따로다.

**5 는 검사 자체가 눈이 먼 것이다.** `30_nar_check` 는 `tts_input` 과 받아쓰기를 대조하는데
**둘 다 옛것이면 서로 맞는다** — 앞단이 움직이면 검사도 같이 움직인다.
잡은 것은 자막이었고, **이 공정에서 대본과 직접 대조하는 자리가 거기뿐이었다.**
막는 방법은 **입력의 판본을 산출물에 박아 두는 것**이다(`10` 이 씬별 대본 지문을 남기고
`30`·`40` 이 대조한다). 검사를 하나 더 만드는 것으로는 안 된다 — 새 검사도 같은 사본을 본다.

**4 의 값은 「5px 를 찾았다」가 아니다.** 그 0.4% 를 「그런 자리는 이렇게 피하세요」로
**넘겼더니 받는 쪽이 그 전제로 설계를 쌓았다** — 연출이 시간축에 `linear` 를 네 자리
박았고, 고치고 나니 그중 셋이 필요 없었다.

```
넘기면   받는 쪽이 그 전제로 설계한다. 전제가 틀리면 설계도 틀린다
고치면   아무도 그 전제를 알 필요가 없다
```

**작아서 안 고칠 것이면 넘기지도 마라.** 넘기는 순간 그것은 남의 설계에 들어간다.
